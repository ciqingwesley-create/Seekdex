# Windows 本地 OCR 验证报告

日期：2026-10-07。代码增加独立 OCR 模块，未更换 Chinese-CLIP、重建用户 embedding、增加人脸识别或进行 Ubuntu 适配。

## 方案与环境

- RapidOCR 3.9.2，PP-OCRv6 small 检测 / 识别，PP-OCRv4 文字方向分类。固定官方 ONNX 文件并校验 SHA256。
- small 三文件 31,749,509 字节（30.28 MiB）；medium 对照 139,334,970 字节（132.88 MiB）。模型不加入 Git。
- Windows 11 10.0.26200；Intel i7-8700，6 核 / 12 线程；Intel UHD Graphics 630；约 24 GiB RAM。
- ONNXRuntime 1.30.0、OpenVINO 2026.4.1。ORT intra-op 4 / inter-op 1，OpenVINO CPU 4 线程 / 1 stream，使用 FP32，未做量化。
- RapidOCR 上游 OpenVINO 集成固定 CPU；本项目保留其前后处理，替换三个推理 session，实际编译 CPU / GPU / AUTO，识别字典从本地 ONNX 元数据加载。
- [RapidOCR](https://github.com/RapidAI/RapidOCR/blob/main/LICENSE) 与 [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR/blob/main/LICENSE) 采用 Apache-2.0；ONNXRuntime 为 MIT。见项目第三方声明。

## 样本与计时

后端对比使用同一组 **27 张**：24 张预先定义文字的受控图（1080×1920 手机布局、3840×2160 大截图布局、6000×4000 招牌布局，各 8 张）、1 张 [RapidOCR 官方公开中文广告样图](https://www.modelscope.cn/models/RapidAI/RapidOCR/resolve/master/resources/test_files/ch_en_num.jpg)、1 张本地真实 Sony JPEG、1 张真实 Nikon NEF 副本。NEF 只读取内嵌预览，未进行 RAW demosaic。

受控图是绘制的测试图，**不是用户真实手机截图或实拍招牌**。真实 JPEG / NEF 没有人工确认的文字关键词，只计性能。当前没有收到用户真实截图 / 相机文字样本；因此不能据此声称已测完真实手机截图、复杂路牌或用户相册的实际准确率。

每张都正常读取、OCR、保存原始文本和文字框、更新 FTS5。每次使用全新的临时 SQLite，以 8 张为批次提交，所有数据库完整性检查为 `ok`。加载 / 预热在吞吐量之外单列；系统文件缓存没有强制清空，不是 HDD 冷读成绩。GPU 第一次动态形状编译比 CPU 慢，首次启动耗时不能用稳态速度代替。

## 后端实测：small，输入长边 2048、检测长边 1536

| 后端 | 实际设备 | 张/秒 | 检测总秒 | 识别总秒 | SQLite 总秒 | 峰值工作集 MiB |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| ONNXRuntime CPU | CPU | 0.481 | 49.251 | 1.713 | 0.0144 | 939 |
| OpenVINO CPU | CPU | **0.787** | 26.508 | 2.047 | 0.0194 | 1641 |
| OpenVINO GPU | GPU.0 / UHD 630 | 0.214 | 85.584 | 35.308 | 0.0228 | 2666 |
| OpenVINO AUTO | 启动时报告 CPU / GPU.0 | 0.374 | 60.833 | 5.769 | 0.0133 | 2833 |

读取 / 解码 / 缩放总耗时分别约 4.52 / 4.97 / 4.87 / 4.83 秒。模型加载分别约 0.83 / 1.19 / 15.49 / 2.41 秒；ORT / CPU / AUTO 预热约 1.84 / 0.77 / 2.89 秒。GPU 首轮预热未单独记录，未把它计入 126.46 秒的测量循环。

主要耗时为文字检测，数据库不是瓶颈。本组 OpenVINO CPU 比 ORT 快约 **1.64 倍**。UHD 630 确实执行模型，没有把回退 CPU 的数据记为 GPU。自动设置已依据完整基准选择并缓存 **OpenVINO CPU**；CPU / GPU / AUTO 的标准化文本在这组图上与 ORT 完全一致。其他机器首次自动设置会用少量待处理图片测量，结果不保证同样选择。

Windows GUI 两次继续任务测得约 0.94–1.14 张/秒；它不含已取消任务中的前 2 张，且与独立基准的样本顺序、初始化和进度口径不同，推荐比较上表同组完整测量。

## 输入尺寸与 medium 对照

使用相同 10 张子集（含真实 JPEG、NEF、公开样图和受控布局），21 个预定义关键词：

| 模型 / 输入长边 | 张/秒 | 关键词命中 | 峰值 MiB |
| --- | ---: | ---: | ---: |
| small / 1024 | 3.397 | 21/21 | 744 |
| small / 1536 | 1.896 | 21/21 | 985 |
| small / 2048 | 1.267 | 21/21 | 1308 |
| medium / 2048 | 0.441 | 21/21 | 2134 |

medium 没有增加本组目标关键词命中，速度和体积成本更高，因此界面使用 small。缩小输入速度更快，但本组多为清楚大字，不能证明 1024 能覆盖密集截图的小字；默认保留 2048 的裁剪输入和 1536 的检测上限。输入策略参与 OCR 模型 ID，调整策略不会悄悄复用不同策略的结果。

## 质量与全文检索

清单：[ocr-quality-manifest.json](ocr-quality-manifest.json)。其中 25 张有文字的受控 / 公开样图共 **65 个关键词，25 种查询**；真实无标注照片关键词列表为空。清单引用本地验证图片，图片不分发，复测需要提供相应图片或替换为自己的路径。

- 标准化关键词命中：65/65，100%。
- 原始文本严格子串命中：59/65，90.77%；差异主要为中文空格。原文保留，没有改写数字或用语言模型纠正。
- FTS 检索 macro Recall@1：46.67%；Recall@5 / @10：100%。每个查询以全部相关 UID 为分母，同样文字出现在三种布局中，所以 Top-1 无法召回全部相关图片；这不是“首张是否相关”的准确率。
- 指标只统计预定义关键词，**不是整段 OCR 逐字准确率**。公开广告图中装饰大字和小字确实有误识别，例如“直击底价”并未正确还原；相关低置信度原文保留供查看。
- 中文单字 / 双字 FTS5 倒排检索，英文和数字按词；之后做连续关键词校验。主查询不使用全表 LIKE。
- OCR 单独搜索按 BM25；OCR + AI 先限制候选，再按现有 CLIP cosine 排序。不会换 embedding 语义空间。

完整分阶段数值见 [ocr-performance-results.json](ocr-performance-results.json)。前期 26 张、库默认检测尺寸的试验只作探索记录，比较结论采用上表 27 张同组、同策略测量。

## Windows GUI 实际验证

通过真实 Windows Qt 平台显示主窗口，在独立 SQLite 与图片副本上完成：

1. 模型下载、SHA256 校验成功；界面“安装 / 检查 OCR 模型”再次完整校验成功。
2. 选择目录、普通搜索返回 27 张。OCR 中途点击取消，保留 2 张；继续复用 2 张、识别剩余 25 张，失败 0。
3. 再建立索引复用全部 27 张，没有再次解码或推理。
4. `Windows`、`错误代码`、`0x80070005`、`ChatGPT`、`中文菜单`各找到 3 张受控布局；`冰点标准`找到公开广告图。
5. 原始 OCR 详情与高亮成功显示。截图检索已验证；真实用户手机截图、实拍文字照片仍缺少样本，未宣称验证完成。
6. 对少量临时图片建立真实 Chinese-CLIP 向量，`电脑屏幕` + `Windows Update` 返回有 embedding 的 OCR 命中图，cosine 0.34545；另外 2 张 OCR 命中但没有 AI 向量，按既有规则不参与 AI 排序。
7. 通过现有后台整理任务预览 / 移动图片，UID 和 OCR 数据及 indexed_at 完全不变。再次 OCR 复用 1 张。撤销后原路径 / UID / OCR 恢复，文字搜索仍找到 3 张。
8. 索引和查询时设置 socket 连接禁止断言，未触发联网。图片和文字没有上传。
9. 最后一次使用界面“OCR 自动”重跑上述流程，实际采用缓存的 OpenVINO CPU。Qt 20ms 心跳记录 2130 次，最大间隔约 0.234 秒；主界面持续响应。SQLite 完整性 `ok`。结果见 [GUI 验证数据](ocr-gui-verification.json)。

验证过程中修复：新增状态线程在关闭窗口时继续启动任务的问题；普通结果切换后的详情残留；缺少目录覆盖状态时 OCR 没有优先查询缓存；渐进扫描与 FTS 的英文词边界不一致。验证脚本的详情对话框等待时序也修正后重跑成功。

## 测试与限制

原有 208 个测试全部保留，新增 50 个 OCR 测试，**258 个全部通过，退出码 0**。假后端测试不依赖真实 OCR 模型，覆盖迁移、原文 / 更新、FTS 中英数字、组合过滤、取消继续、缓存复用、移动 / 撤销 / 复制、图片修改、模型 / 预处理版本、RAW 预览、损坏图片、空文字、后端缺失 / 回退、批量事务和 FTS 恢复。

限制：极小字、装饰字体、弯曲 / 模糊文字、密集或很长截图可能漏字；RAW 预览质量受相机内嵌版本限制，没有自动高质量 demosaic；没有拼音、编辑距离纠错或复杂版面分析。仅以大小 / 纳秒 mtime 判断内容变动，不能检测人为保持两者不变的替换。外部修改需要刷新或再次建立 OCR 索引；没有实时监控。首次自动调优及 GPU 编译可能较慢，允许当前单图完成后取消。
